# Web UI

The `bbbench serve` command (also started automatically by `orchestrator` during a run) exposes a web interface on `http://0.0.0.0:12345` by default.

## Benchmark Status

The **Status** page shows live progress while `orchestrator` is running.

- **Current Status** — running/idle indicator, overall progress bar, current phase number, and completed phase count.
- **Drives** — one card per benchmarked drive showing model, serial, capacity, current status, and active phase name, then its configuration (below) and its phases.

- **Run group** — during a setting test a banner above the drives reads `Setting test: <setting>, run <i> of <n>, <step>` with the strategy and an ETA that covers the runs still to do (`ETA unknown` when a phase has no known length). Each drive card shows its value and `before`/`after` badges (`pending`, `ok`, `failed`; the reading and the kernel's value are in the tooltip), `invalid` when the drive did not hold the value, and `restoring` while the group restores. Nothing changes outside a run group; the restore outcome is on the group page.
- **Layout groups** (storage layout setting test) — the banner also names the run's layout, `run <i> of <n> (layout <label>)`, and the steps read `building the layout`, `resyncing <x>%` (bbbench waits for the initial resync to finish before measuring) and `tearing down`; the ETA leaves the resync time out. The benchmark target is a composite: an md array (`md127`) or a logical volume (`dm-3`), drawn as `<name> (SSD) · array`. Its card shows the configuration of the array node itself once read (interface `md` or `device-mapper`, the kernel write cache, and the Queue, md and dm_mod lines below; the node has no SMART, slot or link), then the member disks: name, model, serial and role (`data`, `spare`, `journal`), with each member's interface, queue mode and SMART health once read. Drive cards show `tearing down` while the layout is removed.

Each drive card also shows how the disk is configured, read once when the run starts (read-only: reading it changes nothing; bbbench changes a drive's setting only in a setting test, see [Run Groups](#run-groups)):

| Line | Meaning | Source |
|---|---|---|
| Interface | `NVMe (PCIe)`, `NVMe (tcp)`, `SATA`, `SAS`, `USB`, `virtio` | sysfs |
| Slot | where the disk physically sits: the SES enclosure slot or SAS bay for SAS/SATA drives behind an HBA, the SMBIOS system slot (type 9) for NVMe, the kernel's PCI slot table when SMBIOS is unreadable, or the SMBIOS onboard device (type 41) with the SATA port | sysfs, SMBIOS |
| Controller | what it hangs off: NVMe controller, SATA (AHCI), SAS HBA, RAID controller, USB, virtio, with its name, driver, PCI address and IDs, firmware and BIOS version and SAS address. Behind a RAID controller it says whether the disk looks like a **RAID virtual drive** (the physical disks are hidden: benchmark, SMART, temperature and slot are the volume's) or a passthrough disk. | sysfs, `lspci` |
| Link | negotiated link, e.g. `8.0 GT/s PCIe x4`, `6.0 Gbps`; the maximum is shown when known, with **below max** when the link runs slower (bad slot or cable, or the link saving power) | sysfs |
| Power | NVMe power state and APST (`nvme get-feature`), runtime PM, PCIe ASPM policy and link state, SATA link power policy | sysfs, `nvme` |
| Write cache | the kernel's policy (`write back` or `write through`: only write back drives get Flush commands) and the drive's own cache (enabled or disabled) | sysfs, `nvme`, SG_IO |
| SMART | health (`PASSED` / `FAILED`) with temperature, wear, power-on hours and error counts | `smartctl`, else `nvme smart-log` |
| Queue | the request queue: `blk-mq: yes, 4 hardware queues, scheduler none` or `blk-mq: no (bio-based)` (md and bio-based dm nodes), then the offered schedulers, `nr_requests`, `rotational`, `read_ahead_kb`, `max_sectors_kb`, `wbt_lat_usec`, `rq_affinity`, `nomerges`, `io_poll`, a SCSI device's `queue_depth` and an NVMe controller's `queue_count` and `sqsize` | sysfs `queue/`, `mq/` |
| md | an md node (or a dm-raid node that shows its md state): level, member count, chunk size, stripe cache size, sync action, bitmap location | sysfs `md/` |
| dm_mod | whenever `dm_mod` is loaded, and on a dm node: its `use_blk_mq`, `dm_mq_nr_hw_queues` and `dm_mq_queue_depth` parameters (`n/a (not on this kernel)` for one this kernel lacks: `use_blk_mq` is gone from newer kernels), and a collapsed list of every dm_mod parameter; `not loaded` on a dm node without it | `/sys/module/dm_mod/parameters/` |

Some of these need root (the SMBIOS table is readable by root only; without it the slot falls back to the kernel's PCI slot table, which needs no root, and may be empty), and SMART needs `smartctl` (smartmontools) or, for NVMe, `nvme-cli`. A line that cannot be read is left out, and SMART says why it is unknown.

The same information, in full, is written to a text file per disk in the run's output directory, `<device>_diskinfo_<start time>.txt` (one per run, so a resumed run keeps what the first one saw). It holds the summary, every sysfs value read, and the complete output of each command, including the reports the summary is drawn from: `smartctl -x`, and `nvme id-ctrl`, `nvme id-ns` and `nvme smart-log` for NVMe or `hdparm -I` for SATA. A command that failed (no root, tool not installed) is listed with its error, so the file shows what could not be read. It also holds the full queue and scheduling dump of the device (and, for an array node, of every device below it) and the queue-related kernel module parameters, see the README, [Queue and scheduling dump](../README.md#queue-and-scheduling-dump).

Each drive's **Phases** list shows its time as it goes: before a phase runs, its expected length (`~5m`, or `length unknown` for a full-disk write); while it runs, the time elapsed against the expected one; once it has finished on that drive, the real time (`took 5m 2s`, with the expected one beside it, finished phases struck through). The header sums the real time spent so far and gives an ETA for what remains. The ETA adjusts as phases finish: the expected length of the remaining phases is scaled by how the finished ones really compared with theirs (fio's setup and ramp-up, a slower drive, ...), and the running phase counts down from that. Phases of unknown length are counted apart, not guessed.

The page auto-refreshes so you can monitor a long run without manually reloading.

## Browsing Results

The **Results** page lists every run found in the output directory (time, ID, mode, drives, phases) with a search box (ID, mode or drive name). Each row links to its **Details**, **Summary**, **Graphs** and **Compare** pages.

The runs of a setting test (run group) are listed under one expandable row for their group, placed where its newest run is: the setting and its values, the strategy, how many runs are listed and their status, and links to the group's **Details** (the group page) and to its **Graphs** and **Compare** (`/graphs?group=`, `/compare?group=`). The ▸ button shows or hides its runs. Each member run names its group (a link to `/group?id=`) and the value(s) it ran under; the search box also matches the group ID and values. Single runs are listed as before. `/api/results` carries `group_id` and `setting_values` for member runs only.

- **Details** shows the run's overview, its drives, and its phases with duration and job count. A phase that did not run on a drive (`--skip-write-through`) shows the reason, and a phase that ran with a caveat, such as a write-through drive that never receives a Flush, shows the warning with how to check and fix it. An **Export HTML** button downloads a standalone report. For a run of a run group, a **Run group** card links to the group (and its graphs and compare) and lists each drive's setting, value, the readings before and after the run (with the kernel's value), and whether the result is valid, with the reason when it is not. A run on an array target adds a **Drives** card that lists the target with its member disks and their roles (`/api/results/detail` carries them as `Members` of the drive).
- **Summary** is a table of statistics (min, average, max and standard deviation) per phase, broken down by disk.

## Run Groups

A setting test (run group, see the orchestrator) is served at `/group?id=<group id>`. The page shows the setting, its values, the strategy, host and plan, then a table of runs by drive: the value, the reading before and after the run (with the kernel's own value, for the write cache the `write_cache` of the block device), whether the result is valid, and a link to the run. When a phase of a run carried a write-through warning, the row says so, which explains missing Flush data. Below come the result of restoring the original values and a matrix of the main metrics (IOPS and MB/s: mean, min-max and n) per phase and value, taken over valid results only; a value with no valid result is shown as incomplete. A group that is still running refreshes by itself and appears while it runs.

A layout group (storage layout setting test) adds a **Layouts** card listing each run's layout label with its disks (name, model, serial, role). In the runs table an array target is written `<name> · array` with its members below (`members: sdb (data), sdc (spare)`), the kernel reading is prefixed `layout:` (the array or volume state, such as `array_state=clean`), and each run says `torn down` or `teardown failed on <names>`. The last card is **Teardown** instead of Restore: `Torn down.` or `Teardown failed on: <names>` (the layouts still assembled, to tear down and wipe by hand, see the recovery offer at the next start). Values compare by their label string, so the same layout in two runs is one value of the matrix.

The same data is available as JSON: `/api/groups` (list), `/api/groups/detail?id=` (group file, per run summary, kernel readings, `flush_note` and the matrix; for a layout group also `variants`, each run's `teardown`, and per drive `kind: "array"`, `uuid` and `members`) and `/api/groups/graphs?id=` (the graph data of the member runs together; each entry carries `setting_value` and `run_id`, and `invalid` for results that did not verify; the results of an interrupted run are kept but marked `invalid`, since the setting was not verified after it; runs that were not run contribute nothing).

## Graphs and Navigation

The **Results** page lets you explore time-series charts from a completed (or in-progress) run.

The left sidebar provides filters that update the displayed graphs in real time:

| Filter | Description |
|--------|-------------|
| **Graph Type** | Toggle IOPS, Bandwidth, Latency, Flush latency, Device latency (ftrace) and Block-layer latency (ftrace) charts independently. |
| **Drive Type** | Narrow down to HDD or SSD results. |
| **Vendor / Model / Serial** | Select specific hardware identities. |
| **Disk** | Choose which drives to include. |
| **Phase** | Select one or more benchmark phases (e.g. `seqread`, `randread-randread`). |
| **Setting value** | Run groups only (`/graphs?group=<group id>`, and a member run of a group by its own `/graphs?id=`): the values of the setting (e.g. write cache `enabled`/`disabled`), to show or contrast the variants. |
| **Hide invalid results** | Run groups only (the group, or one of its member runs by id), on by default: results whose drive did not hold its value are left out. Unchecked, they are shown and their cards say `(invalid)`. |

`/graphs?group=<group id>` shows the member runs of a group together (`/api/groups/graphs`); `/graphs?id=<run id>` shows one run; a member run of a group viewed by its own id still carries its label, so it gets the **Setting value** filter and hides invalid results by default, while a plain run shows neither. In a group, a card is titled `disk · value`, and `disk · value · round N` when a value was measured in several runs (parallel-swap), since the same disk appears in each run. A card of an array target adds its members to the subtitle (`members: sdb (data), sdc (data), sdd (spare)`), and so does the enlarged chart's title.

Each matching combination of disk × phase is rendered as its own graph card. Click a card to maximize it; press **Esc** to return to the grid.

**Units.** A chart plots its metric in the base unit and prints the numbers with an SI prefix letter: bandwidth in bytes/s (fio's KiB/s * 1024, so `2.4G` is 2.4 * 10^9 bytes/s, and 2300 MiB/s reads `2.41G`), IOPS, and latency and Flush latency in seconds (`800μ`, `2.5m`). The prefix (k, M, G, T, P; for seconds n, μ, m) is chosen from the largest value of the phase, so every card of a phase uses the same one, with the axis headroom left out (a 900 MiB/s peak reads `944M`, not `0.94G`). The y axis is titled with the base unit (`bytes/s`, `IOPS`, `s`), ticks show the prefixed number (`1.5G`) and the hover adds the unit (`Read: 2.41G bytes/s`, `Stack total read: 2.41G bytes/s`). The data is unchanged. The compare chart picks its prefix the same way from the largest value it plots, its axis title names the base unit (`Bandwidth (bytes/s)`).

**Time axis.** All time-series graphs use one x axis, in seconds from the start of the phase, from 0 to the longest series shown, so cards line up. fio's `ramp_time` is shaded as **ramp-up**: fio logs nothing during it, so the fio curves start where it ends. A point is the average over one polling window (`--log-avg-msec`) and is drawn at the start of its window; hover it to see the window. fio stamps the end of a window, so its points are moved back by one window, which keeps the first point at the end of the ramp-up instead of one interval later.

**Graph mode.** An IOPS or Bandwidth phase with per-member data has a Normal | Stacked toggle in its header, Normal by default: Normal draws every member drive as its own unfilled line (read up, write mirrored down) together with the array's fio lines, each at its own value (no stacking, no `Stack total` in the tooltip), and the y axis is the largest single shown value; Stacked (described next) stacks the members. Latency is never stacked (one line per member either way), so a latency phase has no toggle. The y axis is recomputed and the choice lasts until the page is reloaded.

**Array phases.** For a run on an array target (md or LVM layout) the IOPS and bandwidth charts stack the members (data, spare and journal disks): reads up, writes mirrored down, one area per member, with the array's own fio series as a line outside the stack; hovering lists each member, `Stack total` and the array value. Latency has one line per member and direction and is never stacked. The member values come from the kernel's counters on each member (`/sys/block/<dev>/stat`, sampled once per `--log-avg-msec` window and stored in `<fio log prefix>_members.1.log`, served as `ts_members`), so they include md/LVM overhead (parity, mirroring, read-modify-write, resync) and the stack total can exceed the array value. Member latency is the kernel's per-request time (queue plus service, 1 ms tick resolution, coarse at low load); the array line is fio's. Runs made before this feature have no member series, and the compare page does not draw them. **md state track** (md arrays only): the sampler also stores the array's `sync_action`, `sync_completed`, `sync_speed`, `degraded`, `array_state`, `raid_disks` and each member's state (`/sys/block/<array>/md/`, served as `ts_md` and `md_events`). Windows where `sync_action` is not `idle` get an opaque strip across the top of the plot with the action (resync, recover, check, repair, reshape, frozen) and a light tint; every change between two windows is a vertical marker with its text (`sync_action idle -> check`, `degraded 0 -> 1`, `sdb: in_sync -> removed`), a non-idle `sync_action` or a `degraded` count above 0 present at the start is marked `(at phase start)` (a faulty member or non-clean `array_state` present at the start is not reported until it changes), and an unreadable value is not a change. The hover adds `md: <action> <pct>% <speed> MiB/s, degraded <n>` for a busy window and `md: idle, degraded <n>` for an idle one; the card shows a badge (`resync 43% -> 61%`, `degraded`) and `array busy: results include administrative work`, since a sync during a phase (a scheduled check, a rebuild, a reshape; the initial resync is still waited for) adds its own I/O to the numbers. LVM arrays and the compare page do not have it.

**Flush latency** is not measured by fio. It carries a different tag (`ftrace`) and has its own clock from the start of the phase: the mean over each window, with no points during the ramp-up. A drive that never received a Flush shows why instead of an empty chart (see [flush-latency.md](flush-latency.md)).

**I/O latency (ftrace)** is measured from kernel trace events (see README, "I/O latency tracing"), not by fio. Two places show it:
- The **Latency** chart adds the traced mean latency as dashed lines next to fio's: device latency (long dashes) and block layer latency (short dashes), read in blue and write in red. The members' ftrace series are not drawn there (an array card shows the kernel-stat member lines and the target's own ftrace lines). A bio-based array target (md, dm, LVM: no request queue) has no device or block layer line of its own; its bio mean is drawn instead, `Array read bio mean (ftrace)` and `Array write bio mean (ftrace)`, dashed, in the array's colours.
- The **Device latency (ftrace)** graph type has its own card per disk and phase: device mean (dashed) and p99 (dash-dot) for reads and writes, and, for an array target, one line per member with its device mean (reads solid, writes dashed). It carries the `ftrace` tag and its own clock from the start of the phase, like Flush latency. A bio-based array target (an md or dm node, which issues no requests) is timed at the bio level instead (`block_bio_queue` -> `block_bio_complete` of the bios submitted to the node): `Array read bio mean (ftrace)` and `Array read bio p99 (ftrace)` (and write), in the array's fio colours and line width, dashed like the device series, next to the members' device lines; series keys `ftrace.bio.mean.r` etc., with their own checkboxes. On a kernel without the bio tracepoints, or a device the kernel does not trace, the card says why (`no request events seen`, or the note of the failed start) instead of an empty chart. Its source line names the device tracepoints (and the node's bio tracepoints) only.
- The **Block-layer latency (ftrace)** graph type is the same for the block layer latency (insert to complete, which adds the I/O scheduler and the software queues): block layer mean (short dashes) and p99 (dash-dot) per direction, each member's block layer mean (`sdb read block layer mean (ftrace)`), its own y range and SI prefix per phase, and a source line naming the block-layer tracepoints, paired first-in first-out by (dev,sector) whatever the device source. A drive without block layer series gets a card that says why, from the data: `no block-layer series: the kernel has no block_rq_insert tracepoint`, `no block-layer series: bio-based (no request queue): ... bio-level latency (block_bio_queue -> block_bio_complete) on the Device latency card` (a bio-based target whose members have none; with members, their lines are drawn and that note is shown under the source line, and in the enlarged chart after it), the NVMe multipath note, or the reason tracing was off. A run (or a selection) with no block layer data at all has no Block-layer card: the section lists the reasons instead.

**Tracepoints behind each ftrace metric** (also the tooltip of the metric's source badge, with the tracepoints monitored in the shown runs listed under each section header):

| Metric (graph type) | Kernel tracepoints (trace events) and the pair the latency spans |
|---|---|
| Flush latency | Device Flush commands. NVMe: `nvme_setup_cmd` -> `nvme_complete_rq` (flush opcode, I/O queues, paired exactly by controller, queue, command id). Any other device, and NVMe without those tracepoints: `block_rq_issue` -> `block_rq_complete` (rwbs `F`, 0 sectors, first-in first-out). A bio-based md/dm node: `block_bio_queue` -> `block_bio_complete` (its flush bios: rwbs `F`, 0 sectors, first-in first-out; the members' flushes included) |
| Device latency (ftrace) | Each read and write. NVMe: `nvme_setup_cmd` -> `nvme_complete_rq` (read and write commands, exact). Any other device (SATA, SAS, HDDs, array members), and NVMe without those tracepoints: `block_rq_issue` -> `block_rq_complete` (first-in first-out per sector). A bio-based md/dm node (array target): `block_bio_queue` -> `block_bio_complete` (its read and write bios, first-in first-out by device, sector and length) |
| Block-layer latency (ftrace) | Every request-based device, NVMe included: `block_rq_insert` -> `block_rq_complete` (a request issued without an insert counts from `block_rq_issue`; merges via `block_rq_merge`), so it adds the I/O scheduler and software queues. None on a bio-based md/dm node |
| Latency chart, dashed ftrace lines | Both of the previous: the Device latency and the Block-layer latency means, and a bio-based node's bio mean |

The tooltip and section header also list the tracepoints actually monitored in the shown runs (`io_trace.devices[].events`, `flush.events`).

- The members' ftrace series appear only on these two graphs. HDDs and other non-NVMe devices use the block tracepoints: device latency is issue to complete, block layer latency insert to complete. The compare page does not draw ftrace latency.

**Legends and source line.** Series are named after what measured them: `Read (fio)`, `Write (fio)`, `Array read (fio)`, `sdb read (kernel stat)`, `Read device mean (ftrace)`, `sdb read device mean (ftrace)`, `Read block layer p99 (ftrace)`, `Array read bio mean (ftrace)`. Under each card (and in the enlarged chart) a source line says which tracepoints each device was timed from, how the events were paired and how many were lost, for example `ftrace: block_rq_issue -> block_rq_complete, block_rq_insert -> block_rq_complete · pairing: first-in first-out (dev,sector) · lost events: 0`. A loss count above 0 also gives the card the warning `⚠ N trace events lost: the ftrace series are incomplete`; the breakdown `(ring buffer N, unpaired M)` is in the source line. The Details page lists the same line and the reason when a device could not be traced.

**Showing and hiding series.** Each card and the enlarged chart have a row of checkboxes, one per series (a dashed swatch for dashed lines). Unchecking one removes it from the chart, from the stack of a stacked array chart (the members left are restacked) and from the y scale, which is recomputed from the shown series of the phase so cards stay comparable. Hiding every line does not turn a card into bars. The choice is page memory only: it is kept while the page is open (and across Normal | Stacked) and lost on reload. `Read (fio)` and `Write (fio)` also cover an array's own fio lines.

## Comparing Disks on the Same Graph

The **Compare** view overlays multiple disks on a single chart, making it easy to spot performance differences.

Select two or more drives in the sidebar, choose a phase, then click **Compare**. Each drive is drawn in a distinct color with a legend. Metric, phase, and time axis are shared so curves are directly comparable. Flush latency is a metric there too; it has no read and write sides, so the direction checkboxes do not apply to it. Device latency (ftrace), Block-layer latency (ftrace), the members' series and the series checkboxes are not on the compare page.

For a run group (`/compare?group=<group id>`, linked from the group page and the results list), and for a member run of a group by its own `/compare?id=`, the sidebar adds a **Setting value** list and the **Hide invalid results** toggle (on by default; invalid series are labelled `(invalid)` when shown). Each (drive, run) is its own series, named `disk · value`, or `disk · value · round N` when a value was measured in several runs (with the phase after the disk when several phases are selected). An array target's entry in the disk list names its members.
