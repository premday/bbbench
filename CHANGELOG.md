# Changelog

## [Unreleased]

### Added

- Graphs page: the trace-loss warning (`⚠ N trace events lost`) now says which ftrace series of the card are incomplete and why, from the data: the headline gives the breakdown with thousands separators (`⚠ 1,296,525,622 trace events lost (ring buffer 1,296,000,000, unpaired 525,622): every ftrace series on this card is incomplete`), then one line per cause: the ring buffer overrun (session-wide: every ftrace series of the phase misses events, the card's series are listed by their legend labels, their statistics are a sample of the events that arrived) and each device's unpaired requests, only for the devices with a series on the card, with those series; plus the share lost when the phase summary has counts for the card's kinds. The Flush card gets the same kind of note when Flushes were issued but never seen completing (its session's overruns are not recorded). Card and enlarged chart; text only
- `serve -addr` next to a running orchestrator: `serve` used to refuse whenever an orchestrator ran, whatever its `-addr`, and named a fixed address. The orchestrator now records its web address in the lock file, and `serve` refuses only when it would listen on the same address (a wildcard covers a specific host); on another address it starts, saying that it shows saved results only, not the live run. A lock file without an address (older bbbench) means the default `0.0.0.0:12345`
- `orchestrator --addr <host:port>` sets the address of the web server it starts for a run (it was fixed at `0.0.0.0:12345`, so `-addr` only worked with `serve`); its messages print the real address, the `serve` help line shows the real default, and the "orchestrator is already running" hint no longer names a fixed address
- Graphs page: a **Y scale** selector in the sidebar chooses how cards share a y range and SI prefix: Per phase (default, as before), Global (one range per graph type over all its phases, each phase in its own Normal | Stacked mode, so cards compare directly across phases) or Per graph (each card its own range). Hidden series never count; changing it, a series checkbox or a phase's mode redraws every phase of the graph type and the enlarged chart, keeping checkboxes, modes and folded sections. Page memory only; the compare page is unchanged.
- Graphs page: the x axis is per phase: the cards of a phase (all drives, all shown graph types, the enlarged chart included) share 0..the longest series of that phase, so a 60 s phase is no longer squeezed by a 600 s one; hidden series, the Y scale criterion and the Normal | Stacked mode do not change it. The compare page is unchanged
- Results tab: run groups start expanded; a group is a white line and the runs nested in it are a bright grey line indented as a whole (left bar, timestamp and ID cells pushed in), so groups and their runs are told apart at a glance; the group row's first action is labelled Details, like a single run's
- Status page: an expanded detail (the `dm_mod` parameter list) no longer folds back when the page refreshes every 2 seconds, and a refresh that produces identical markup no longer rebuilds the view at all, so scroll positions, text selections and hovered tooltips survive; the expanded state of every `<details>` is kept per card
- Drives are listed in device-name order in the setup screens (drive selection, layout disks, setting-test drives): numbers compare as numbers (`nvme2n1` before `nvme10n1`) and `sd`/`vd`/`hd` letters in kernel order (`sdz` before `sdaa`), where a plain string sort put `nvme10n1` before `nvme2n1`
- ftrace latency of an array's own node: md and dm nodes are bio-based (no blk-mq queue: `queue/` without `mq/` in sysfs), so the request tracepoints never fire for them. Such a node is now timed at the bio level, `block_bio_queue` -> `block_bio_complete` of the bios submitted to it (kind `bio`, source `bio`, per direction, paired first-in first-out by device, sector and length through the end sector, so a bio the node splits counts once), next to its members' device and block-layer series; its Flush latency comes from its empty flush bios (`Flush (bio)`, the members' flushes included). The bio events are enabled only for bio-based nodes, with a device filter, in the same private session; request-based devices are unchanged, so nothing is counted twice. Log and API: `bio_based=true` and kind `bio` lines in `<prefix>_iolat.1.log` (older logs read as before), `io_trace.devices[].bio_based`, `stats.bio`, the bio pair in `text_device`, a `block_layer_note` pointing at the bio series, `ts_iolat` points of kind `bio`, `flush.source` `bio`; the run summary gives the node's bio latency first. Web UI: `Array read bio mean (ftrace)` and `p99` (and write) on the Device latency card next to the members, the bio mean as a dashed line on the Latency chart, the Block-layer card of such a node draws its members with a note that the node has no block layer, and the badge tooltips and README table list the bio pair. Not verified on hardware: the bio payload formats, whether `block_bio_complete` fires for the node's own bios on md, dm and LVM nodes (`BIO_TRACE_COMPLETION`) and with which sector after a split or remap, and the event counts on real arrays
- Queue and scheduling dump: every disk dump (`<device>_diskinfo_<start>.txt`) now holds the device's whole request queue and scheduling state from sysfs (every readable file under `queue/`, `queue/iosched/` and `mq/<n>/`, blk-mq or bio-based with the hardware queue count and CPU map, SCSI device and host queue limits, NVMe controller queues, debugfs blk-mq state when readable, or a note that the values are sysfs only), every file under `md/` of an md node and `dm/` (and `md/`) of a dm or dm-raid node with the queue of every device below it, and once per file every parameter of `dm_mod`, `md_mod`, `nvme_core`, `nvme`, `scsi_mod`, `sd_mod`, `libata`, the md personalities and the dm targets (`dm_raid`, `dm_thin_pool`, `dm_mirror`, `dm_crypt`, `dm_multipath`), `not loaded` for a missing one. An array run now also writes the dump of the array node itself. Read-only, bounded (64 KiB per file, 4 MiB per device). Status page: a Queue row (`blk-mq: yes, 4 hardware queues, scheduler none`, tunables), an md row and a `dm_mod` row (`use_blk_mq`, `dm_mq_nr_hw_queues`, `dm_mq_queue_depth`, `n/a (not on this kernel)` when absent, and every dm_mod parameter in a collapsed list), on drive cards and on the array node above its members, whose rows show their queue mode (`Info.Queue`, JSON `queue`). Not verified on hardware: the debugfs blk-mq layout, md and dm-raid nodes on real arrays (fake sysfs trees in tests; the plain NVMe and dm-crypt case was read on one machine)
- Graphs page: the tooltip of each ftrace metric's source badge (graph-type list, section headers, card titles; the Latency badge for its dashed lines) lists the kernel tracepoints behind it, NVMe vs every other device, and the tracepoints actually monitored in the shown runs, which also appear under the section header; the Flush summary JSON now carries `events` like `io_trace.devices[].events`. Reference table in the README (I/O latency tracing)
- I/O latency tracing: every phase also times each read and write from kernel trace events and reports it at the device (NVMe `nvme_setup_cmd` -> `nvme_complete_rq`, paired exactly; any other device, HDDs included, and NVMe without those tracepoints `block_rq_issue` -> `block_rq_complete`) and in the block layer (`block_rq_insert`, or the issue of a directly issued request, -> `block_rq_complete`: adds the I/O scheduler and software queues); array members are traced in the same session. Latencies go into in-process histograms (relative error under 2 %), the phase summary (mean, min, max, p50, p99, after the ramp-up) and one point per `--log-avg-msec` window are stored as `<prefix>_iolat.1.log` (run summary keys `io_trace`, `io_trace_series`, `io_trace_notes`), and every figure carries a lost-events count. **On by default**; `--no-io-trace` turns it off. The per-CPU ring buffers of concurrent sessions, Flush sessions included, share a 256 MiB budget (1 to 16 MiB per CPU, Flush at most 8 MiB), and a private tracefs instance (`bbbench-iolat-*`) is used, with stale instances of a killed or crashed bbbench (`bbbench-iolat-*`, `bbbench-flush-*`) removed at every `orchestrator` start whatever its flags and listed by `doctor`. md and dm nodes are bio-based and usually show `no request events seen`, their members are traced. Web UI: the Latency chart draws the traced mean as dashed lines, two new graph types, **Device latency (ftrace)** and **Block-layer latency (ftrace)**, show the mean and p99 of that kind per direction and each member's mean of it (a drive without block-layer series gets a card saying why, a run without any block-layer data no card), each card and the enlarged chart name the tracepoints each series comes from (series are labelled `(fio)`, `(kernel stat)` or `(ftrace)`), and every chart series has a checkbox to show or hide it (page memory only; the y scale follows the shown series). The compare page is unchanged. New package `internal/iotrace`; `internal/flushtrace` gains `Instance` (the private tracefs instance, shared with Flush tracing). Not verified on hardware: the tracepoint payload formats beyond the existing Flush test lines (`block_rq_insert`, `block_rq_merge`, `nvme_cmd_read`), the `ctrl_id` filter field of the nvme tracepoints, the NVMe multipath sysfs layout, requeues, merges that move the start sector and partial completions, the cost of the per-CPU ring buffers and the effect of tracing on the measured I/O
- Graphs page: each phase of a metric with per-member data has a Normal | Stacked toggle in its header. Normal (the default) draws every member and the array as plain unfilled lines, each at its own value (no stacking, no stack totals; the y scale is the largest single shown value); Stacked stacks the members of IOPS and bandwidth. Latency is never stacked, so it has no toggle and no stacked mode. The y scale is recomputed for the mode and the choice is kept per metric and phase until the page is reloaded; more modes can be added to `GRAPH_MODES`
- Status page: each member of an array shows its firmware revision (`Info.Firmware`, read from sysfs), physical slot with the source that reported it (SES, SAS bay, SMBIOS, PCI slot) and link speed (with the maximum and a `below max` warning), next to model, serial, role, interface and SMART. HPE UEFI locations are not read
- Layout screens: `x` on the layout list destroys one existing RAID configuration you select, to free disks that are grayed out because they belong to it. **It erases: the data is not kept, also of arrays and volume groups bbbench did not create.** It lists assembled md arrays, md superblocks without an array, LVM volume groups and orphan physical volumes (IMSM/DDF and other non-native md metadata, md superblocks without a readable uuid, partial, shared, clustered, exported and foreign volume groups, and two volume groups with the same name are listed grayed with the reason), shows everything destroyed with it and every disk under `THIS DESTROYS DATA`, and needs a single `y` (Enter does nothing). It runs `mdadm --stop` and `--zero-superblock`, or `lvremove`, `vgremove` and `pvremove` (and the devices-file entry); it refuses a configuration that is mounted, swap, holds bbbench or its output, has any holder or signature that is not its own, has a disk without serial, changed since it was shown, or whose LVM physical volumes could not be listed, and every configuration when the in-use scan cannot judge the disks; afterwards it re-scans so the freed disks can be selected, and on failure shows what is left with the manual command; each outcome is printed again after the layout screens. It never touches ZFS, btrfs, bcachefs, LUKS, Ceph, DRBD or VMFS signatures, partition tables or filesystems on the disks themselves (what is inside the logical volumes or the array is destroyed with it), and writes no recovery record. Logs written while a setup screen is shown are held and printed after it instead of over it. New optional `Destroyer`/`LeftoverCommander` interfaces in `internal/settings` (`Existing`, the safety gate) and machine-readable causes in `internal/inuse`. Not verified on hardware: the mdadm and lvm command lines and outputs it reads
- Per-member charts for array runs (md and LVM layouts): during each phase the members' kernel I/O counters (`/sys/block/<dev>/stat`) are sampled once per `--log-avg-msec` window and stored next to the fio logs as `<prefix>_members.1.log` (new `internal/diskstat` package); the graphs page stacks IOPS and bandwidth per member under the array's own fio line and draws latency as one line per member and direction. The member numbers include md/LVM overhead (parity, mirroring, resync), so the stack total can exceed the array value; member latency is the kernel's per-request time with 1 ms resolution. Only new runs have it, not the compare page; the run summary JSON (`run_*_summary.json`) also carries `member_series` and `md_series` per phase (N members x 3 series, like `flush_series`); not verified on real arrays yet
- md state on the array charts: for an md array the sampler also reads `sync_action`, `sync_completed`, `sync_speed`, `degraded`, `array_state`, `raid_disks` and each member's state from `/sys/block/<array>/md/` into `<prefix>_members.1.log`; the graphs page marks windows with a sync action (resync, recover, check, repair, reshape, frozen) with a strip and a tint, draws every change of state (including a removed member) as a labelled marker, adds the progress and speed to the hover, a card badge (`resync 43% -> 61%`, `degraded`) and `array busy: results include administrative work`. The md provider still waits for the initial resync, so a sync in a phase is a mid-run one and its I/O is in the numbers. md only, not the compare page; not verified on real arrays (fake sysfs tree in tests, charts checked in headless Chrome only)
- Storage layout setting test: compare ways of assembling the same disks (the no-array baseline, md arrays with the `mdadm` provider, logical volumes with the `lvm` provider: levels, chunk or stripe size, bitmap, spares, journal) by running the whole test plan on each layout. **It erases every disk it uses.** Disks in use (mounted, swap, bbbench or its output, stacked, with an md/ZFS/LVM/LUKS/btrfs/bcachefs signature, LVM physical volumes) are never offered and when the root or output disk cannot be attributed no disk is offered (new `internal/inuse` package); one `y` confirmation; every layout is built, waited on until its resync ends, read back and verified, benchmarked as one md/dm device (workload type from its data members) and torn down on every exit, with its members wiped. The recovery file `/var/lib/bbbench/group-recovery.json` now also records each layout before it is built, so the next start offers the teardown after a crash and refuses to start while it is declined or a member never comes back; a layout that cannot be torn down stops the group and prints the manual commands. The setting interface is generalized (`Lifetime`, `Prepare`/`Apply`/`Read`/`Undo`, `Settler`, `PerDrive`, `CommandHinter.UndoCommand`) and storage layouts are backends (`settings.Backend`) that hardware RAID controllers will plug into. The group file, recovery file, status, group, results, graphs and compare pages show layouts, their members, resync progress and teardown. New optional dependencies: `mdadm`, `lvm`, `udevadm`. Not verified on hardware yet: the `mdadm --create` command line and sysfs values, the `lvcreate` command lines and `lvs`/`vgs`/`pvs` JSON fields, the LVM devices file handling, Flush tracing on md and dm devices (timed at the bio level, see the array-node ftrace entry above) and trim on arrays without discard; known gaps: an LVM devices file that `pvcreate` creates when there was none is not recorded and not removed, and udev could re-assemble md members between `mdadm --stop` and `--zero-superblock` (the wipe then fails busy: a safe teardown failure with the manual command)
- Setting tests (run groups): the orchestrator can run the whole test plan once per value of a setting; the first setting is the drive write cache policy (enabled vs disabled, NVMe `set-feature`, `hdparm -W`, `sdparm WCE`). Values are spread one after the other, in parallel on identical drives, or in parallel with swap rounds (every value measured on every drive subset). bbbench reads each drive's original value, applies and verifies the value before each run and reads it back after (a run whose value did not hold is marked invalid), and restores every drive when the group ends, also after an error or Ctrl+C; a recovery file (`/var/lib/bbbench/group-recovery.json`) lets the next start restore the drives after a crash. `group_<id>_group.json` records the runs, readings and the restore result; `--resume` continues an interrupted group after a confirmation. Web UI: a Group page and `/api/groups*`, the status page shows the group and per drive verification, and the results list, graphs, compare and run details select and overlay runs by setting value and hide invalid results. New packages `internal/settings` and `internal/rungroup`
- The rule that bbbench never changes a drive's configuration is replaced: it changes a drive's setting only in setting-test mode, after an explicit confirmation, verifies it before and after each run and always restores the original; everything else (single runs, the status page configuration, the disk text dump, Flush tracing) only reads
- README lists the files an orchestrator run writes to its output directory
- Status page and disk dump: where each disk physically sits (SES enclosure slot or SAS bay; SMBIOS system slot for NVMe, with the kernel's PCI slot table as the fallback without root; SMBIOS onboard device for SATA) and what controller it hangs off (NVMe, SATA/AHCI, SAS HBA, RAID, USB, virtio) with its name, driver, PCI address and IDs, firmware, BIOS and SAS address, flagging RAID virtual drives (new `internal/smbios` package; `lspci` is an optional dependency)
- `orchestrator` checks its external programs when it starts: a missing `fio`, or an I/O engine a selected workload needs that fio lacks (e.g. `io_uring`), stops the run with what to install; missing `smartctl`, `nvme` or `hdparm` and an unavailable tracefs are warnings saying what is lost. `doctor` runs the same checks
- Status page: the phase list shows the real time of each finished phase (`took 5m 2s`, with the expected length beside it) and the time spent so far, and the ETA adjusts as phases finish: the remaining expected lengths are scaled by how the finished phases really ran against theirs
- Status page: each drive card shows its interface (NVMe/SATA/SAS/USB), negotiated and maximum link speed, power configuration (NVMe power state and APST, runtime PM, ASPM, SATA link policy), write cache policy (kernel and drive) and SMART health (`smartctl`, or `nvme smart-log` for NVMe), read once at the start of a run (new `internal/diskinfo` package); the full information (sysfs values and the complete `smartctl -x` / `nvme id-ctrl` / `hdparm -I` output) is also written as a text file per disk, `<output>/<device>_diskinfo_<start>.txt`
- Status page: each drive lists its phases with a summary of the key fio options (`rw`, `bs`, `iodepth`, `runtime`, ...) and the fio config the phase runs; served by the new `/api/status/phases` endpoint so the 2-second status poll stays small; finished phases are struck through, each phase shows its expected length, and a per-drive ETA sums the known lengths (`time_based` jobs: `runtime` + `ramp_time`) and counts phases of unknown length, such as full-disk writes and trims, separately
- Release workflow rejects tags that are not `vMAJOR.MINOR.FIX` and tags that are not higher than all earlier tags or already have a release (`scripts/check-tag.sh`, `scripts/check-tag-order.sh`, tested in CI; `make check-tag TAG=vX.Y.Z` before tagging)
- `bbbench version` and `check-config --version` print the version, commit and build date, embedded at build time (new `internal/buildinfo` package)
- GitHub Actions CI on every pull request: gofmt, `go vet`, `go test -race`, template validation, and a build of all release archives
- Tag-triggered release workflow publishing static linux archives (`amd64`, `arm64`, `386`) with binaries, documentation, `dist/` config and templates, and `SHA256SUMS`
- `make check` (CI checks) and `make package` (release archives)
- Flush tracing: phases that fsync also report the device's own Flush latency, measured from kernel trace events (NVMe tracepoints with exact pairing, generic block tracepoints for any other device), saved per phase; `--no-flush-trace` disables it. The drive's `write_cache` state is recorded, and a write-through drive, which the kernel never sends a Flush, is reported as such ("ftrace saw 0 Flush commands") instead of "no data"
- The Flush latency is stored next to the fio logs in fio's shape (`<prefix>_flush.1.log`): one line per `--log-avg-msec` window plus the whole-phase summary in the header, a few hundred lines (about 10 KB) per phase instead of one line per Flush; the summary and the series (`flush_series`, `ts_flush`) are read back from it when a run is loaded
- Flush-latency workloads `ssd_fsync_psync_qd1`, `ssd_fsync_uring_qd1` and `ssd_fsync_uring_qd32` (4k randwrite with fsync after every write, 5 minutes each), added to the default `ssd` list
- Run summary shows the mean fsync latency for phases that issue fsyncs
- Workloads can override `ioengine`, `iodepth`, `direct` and `fsync` per job in `bbbench.workloadsdb`
- Release archives ship a `VERSION` file (version, commit, date, arch) and a generated `RELEASE_NOTES.md`; the GitHub release notes are generated from the commits since the previous tag (`scripts/changelog.sh`)
- Web UI: "Flush latency" graph type (graphs and compare pages) drawn from the stored log and averaged over fio's polling interval (`--log-avg-msec`), so it lines up with the fio series; every graph type shows a `fio` / `ftrace` source tag
- Docs and the write-through warning state that a plain run only reads the write cache mode and the user applies any fix (since changed: see the setting-test entry, a setting test can change it)
- `documentation/flush-latency.md` explains what the Flush latency measures, with a diagram of the kernel stack
- Phases that fsync on a write-through device (the kernel sends no Flush) still run, with a warning on the console, the status page and the run details (`warnings` in the run JSON); `--skip-write-through` skips them instead, with the reason shown in the web UI
- With `--skip-write-through`, a drive that sits out a phase while others run it is shown as "Skipped this phase" with the reason on the status page, and the console names it as soon as the phase starts; a parallel phase that ran elsewhere ends "COMPLETE, skipped on N drive(s)"
- All time-series graphs share one x axis starting at 0 (the start of the phase) and spanning the longest series shown; fio's ramp-up (`ramp_time`, saved as `ramp_sec`) is shaded and fio's points start after it. Points are drawn at the start of their averaging window (fio stamps the end, so its points are moved back one window and there is no gap after the ramp-up); the Flush series has no points and no summary contribution for the ramp-up, like fio (`offset_ms` in the flush log header)

### Changed

- Graphs and compare pages show values with an SI prefix on the number and the base unit after it: `2.4G bytes/s`, `1.2M IOPS`, `2.5m s` (ticks `2.4G`, `1.2M`, `2.5m`, `800μ`; the y axis is titled `bytes/s`, `IOPS` or `s`) instead of thousands of MB/s or μs. The prefix is chosen from the data maximum of the phase (all cards of a phase share it, the axis headroom is left out) or of the compare chart. Bandwidth is plotted in bytes/s (fio's KiB/s * 1024), so `2.4G` is 2.4 * 10^9 bytes/s (2300 MiB/s reads 2.41G); latency in seconds. The data and JSON are unchanged
- The orchestrator drops the template's `log_avg_msec=30000` from the fio files it runs, so `--log-avg-msec` (default 1 s) is the only polling interval. The file's value could override the flag, giving 30 s points and a 30 s blank after the ramp-up on the graphs; hand-run fio on a generated file keeps the 30 s
- CI workflows use Node 24 action versions (`checkout@v7`, `setup-go@v7`, `upload-artifact@v7`) and run on `ubuntu-26.04` instead of `ubuntu-latest`
- `make` builds with `CGO_ENABLED=0` instead of musl-gcc: the code is pure Go, so binaries stay static without a C toolchain
- Generated fio log names and the fioplot `iodepth` reflect a workload's effective iodepth and `direct`/`buffered` mode (unchanged for existing workloads)

### Fixed

- fio log points stamped a millisecond early (9999 for 10 s) no longer fall into the previous 1 s bucket, which merged two windows and left a gap after them

## [0.1.0] - 2026-03-31

This is the first usable release.

### Added

- Orchestrator command for benchmarking multiple drives sequentially or in parallel
- Drive selection TUI with keyboard shortcuts (space to toggle, `a`/`n` for all/none)
- Resume capability for interrupted benchmark runs
- Interrupt handling with graceful shutdown
- Dry-run mode for the orchestrator
- Drive filtering options (`--include`, `--exclude`)
- Verbose mode for detailed execution output
- Web server GUI (`bbbench serve`) with live status, results browsing, and graph visualization
- Auto-refreshing status page during benchmark execution
- Persistent benchmark results with JSON summary files
- fio JSON parsing and per-job metric extraction (IOPS, bandwidth, latency)
- Time-series log parsing with configurable coalesce threshold
- Incomplete-point detection when fewer threads than expected contribute to a sample
- Graph view (`/graphs`) with sidebar filters, foldable sections, chart cards, click-to-maximize
- Compare view (`/compare`) to overlay multiple disks and/or phases on a single chart
- Summary page with aggregated per-disk metrics across phases
- HTML export functionality for sharing benchmark results offline
- `fulldisk: true` in fio job files emits `size=100%`; recorded in fioplot output
- Apache 2.0 license

### Changed

- Removed Criteo-specific naming; codebase is now generic
- Rewrote README to be usage-oriented
- Removed unused YAML config entries (`fioplot` theme/x/y settings, `bbbench.default.template*`)
- Removed `BBBenchConfig.Default` struct (fields were never accessed)
- Trim and blkdiscard phases are hidden by default in both graph views
- Y-axis scaling: baseline at 0 for read-only phases, ceiling at 0 for write-only phases, bidirectional when both read and write data are present

### Fixed

- fio JSON parse failures caused by large-device warning preamble in output
- IOPS aggregation across multiple jobs
- Drive status display (running / complete / pending states, `Device` field population)
- `wait_for` errors across phase boundaries in generated fio job files
- Template rendering bug that caused the orchestrator to find zero jobs
